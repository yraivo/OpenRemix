# Remix 1.6.3 混淆样本逆向分析与源码恢复技术文档

> 本文档系统记录针对历史混淆样本 **Remix `1.6.3`** 建立逆向分析与源码恢复管线的全过程，内容涵盖保护层拆解、副作用受控的常量折叠、JVM 与 Java 源码表达差异处理、安全审计以及编译后运行时缺陷定位。后续 **`1.7.1`** 版本的跨版本迁移与独立 Gradle 构建重构详见 [Remix-1.7.1-Recovery-WP.zh-CN.md](Remix-1.7.1-Recovery-WP.zh-CN.md)。

## 1. 研究目标与样本画像

分析对象为一份无上游工程与源码的 Remix `1.6.3` 历史归档 JAR：

```text
Remix_v1.6.3_untrusted.zip   SHA-256: 4d60b9a4b89e5a7333a5e17aa61e0ffcb3a22441d1fbb53dc7e764bb072d7d64
untrusted-Remix.jar          SHA-256: cfb8ece531effa56caabacb7dcfd6714753a8903893458457f1784a434f6ca1c
```

纯静态扫描（不加载、不执行样本类）所得基础统计如下：
- 归档共包含 **37,414** 个 `.class` 条目，其中 `remix/` 包下标准 class 为 **3,444** 个，另有 **11,311** 个无法按常规 class 文件直接解析的伪装载荷。
- Manifest 含 `Obfuscated-By: Paramorphism` 声明，加载器字节码呈现 Paramorphism 风格的遮盖 gzip 载荷结构；`1.6.3` 样本中不含自定义 `.dll` / `.so` / `.dylib` 原生保护文件。
- 在 `remix/` 标准类中，65 个类的常量池包含 `InvokeDynamic`（共 128 项），1,377 个类直接引用 `javax/crypto/Cipher`。

### 工具链职责划分
- **ASM 与自研 Python / Java 静态工具**：负责 ZIP 解析、载荷解码、副作用受控的常量折叠、调用代理展开、稳定标识符映射及字节码等价校验。
- **CFR `0.152` + Vineflower `1.12.0`**：作为双视图反编译器交叉对照，用于暴露控制流歧义与反编译器遗漏；所有语义判断均以原始字节码为唯一依据。
- **Temurin JDK 8**：负责目标客户端编译及 Java 8 语义验证。
- **隔离测试来宾与本地协议夹具**：在无公网受控环境中执行单人世界持久化、区块重载及协议 `47` TCP 回归测试。

## 2. 副作用审计：修正通用常量折叠的语义破坏

初期尝试直接串联通用字节码清理流程（`NopRemover → RedundantGotoRemover → ConstantFolder`）后，反编译结果显著简化；但在追踪类静态初始化器（`<clinit>`）时，发现原始 `PUTSTATIC` 指令遭到错误删除。

针对该现象，对原始输入与折叠输出逐类统计方法调用及字段写入指令的签名与出现次数：

| 审计指标 | 1.6.3 | 1.7.1（同期对照） |
| --- | ---: | ---: |
| 参与比对的类总数 | 3,454 | 3,588 |
| 方法调用或字段写入次数发生变化的类 | **803** | **854** |
| 计数减少的指令出现总次数 | **11,392** | **11,884** |

该结果表明，仅依据反编译代码整洁度评估去混淆效果存在严重失真。项目随后废弃激进折叠产物，**回退至原始字节码重新实现保守整数折叠器**：
- 仅对相邻字面量构成的确定算术与位运算按 JVM 整数溢出及移位规范求值；
- 保留可能改变异常边界的运算（如除零），不基于未知条件分支裁剪代码块；
- 每次改写后执行 ASM 校验，未通过校验的类整类保留原始字节码。

改造后，在 `1.6.3` 上共折叠 **1,468,756** 处表达式（覆盖 2,752 个类，2 个类保留原输入），**方法调用与字段写入签名计数变化均为 0**。此阶段确立了核心工程原则：**原始字节码是语义依据，反编译可读性仅是衍生结果；所有变换均须可核对。**

## 3. 静态拆解加载层与隐藏载荷

### 3.1 伪装 `.class` 载荷解码与身份隔离
在 37,414 个 `.class` 条目中，有 **11,311** 个条目的文件头被改写为 `CAFEBABE` 以伪装成 class 文件，实质为 gzip 压缩载荷。通过静态解析加载器 `<clinit>` 中的资源定位字符串，并在 ZIP 目录中执行唯一匹配（806 项直接匹配，10,505 项经循环移位唯一匹配，存在歧义一律拒绝），可完成纯静态解码：

```python
# 伪代码：纯静态读取 ZIP 字节，不触发样本加载器执行
resource = unique_zip_match(resource_text, rotations=True)
packed = bytearray(zip_read(resource))
packed[:8] = bytes.fromhex("1f 8b 08 00 00 00 00 00")  # 还原标准 gzip 文件头
payload = gzip_decode(packed)
parse_class(payload)
save_by_loader_path(payload)
```

上述 **11,311** 份载荷全部成功解压并通过 ASM 解析（注：原始样本拆解阶段解析出 11,311 份载荷，最终审计构建归档中保留 10,368 份隐藏载荷，两者属于不同构建阶段，并非类丢失）。

该保护层存在一项关键特征：**所有隐藏载荷的内部类名均为 `?`**，在运行时依靠各自独立的类加载器隔离身份。若在分析或审计中仅按内部类名去重，将导致大量隐藏类发生覆盖合并，进而遗漏敏感调用链。因此整个索引与审计体系均以 `archive_location + internal_owner + name + descriptor` 作为唯一节点标识。

### 3.2 方法代理与常量提供器展开
完成载荷解码后，为各加载器建立索引并处理两类高频模式：
- **常量提供器**：无参数 → `ldc <String>` → `areturn`（保守重建替换 **13,506** 处；字符串以原始 UTF-16 代码单元存储，避免非配对代理字符在编码转换中损坏）；
- **调用代理**：按序压栈参数 → 单次目标调用 → 按目标类型返回（在参数、返回值、接收者及调用 opcode 均严格匹配且满足访问与初始化边界时展开，替换 **58,545** 处）。

对于仍需在源码中保留的辅助实现，将其重构为可编辑 Java 模板（如 `RecoveredDelegatePayload`、`RecoveredLiteralPayload`）：
- 调用桥核验 **1,058** 个目标方法签名与调用指令一致（另记录 49 处 `javac` 插入的常规引用 `checkcast`）；
- 共享提供器核验 **2,048** 个 getter，小提供器核验 **3,424** 份（其中 3,423 份逐字节一致，仅 1 例因 Windows 保留设备名 `i/n/con` 采用合法源级别名）。

## 4. 动态缓存与枚举恢复边界

对于固定参数、无外部状态依赖的 XOR / Base64 算法，可直接离线求值；但涉及 DES/AES 解密、共享缓存及静态初始化依赖的对象，不可将单次冷启动结果静态固化为常量。

典型反例为分类枚举 `MD`：
- **冷缓存状态**下，`HIDDEN` 枚举项标签为空字符串；
- **预填共享缓存**后，原版标签解析为 `!`。

若仅以冷启动输出替换动态逻辑，虽然能够通过编译，但会破坏真实数据流。最终方案在源码中采用合法 Java 枚举常量，保留原有动态解码、颜色提供器与共享缓存访问逻辑，并通过**冷态、热态、污染缓存及异常注入**多组隔离测试验证动态行为等价。

## 5. JVM 与 Java 源码的表达差异处理

### 5.1 双层源码表示与反编译器遗漏
混淆字节码合法并不意味着可直接表示为合法 Java 源码。典型障碍包括 Windows 大小写与保留设备名冲突、包与类型同名、仅以返回类型区分的重载方法、`super()` 前置求值顺序、`bridge`/`synthetic` 访问标志以及异常签名约束。因此本阶段采用双层构建模型：

```text
合法、可编辑的 Java 源码 ──► javac ──► 受资格约束的 119 步后处理配方 ──► 目标 JVM 结构
```

所有业务逻辑必须源自本次 `javac` 编译结果，禁止回填原混淆 JAR 的方法字节码。

此外，针对反编译器默认隐藏合成方法的问题，对 34,917 个分析方法统计显示，其中 **34,748 个带有 `synthetic` 标志、9,055 个带有 `bridge` 标志**。Vineflower 必须显式启用 `--no-remove-bridge`，否则大量方法会在反编译输出中静默缺失。

### 5.2 三类批量根因修复
- **静态初始化器 `<clinit>`**：拆解准备、解码、发布与业务后缀阶段，保持注册表与常量发布的原始时序（核验 485 个分段字符串表与 73 个单字符串表，覆盖 7 万余条规范化指令）。
- **泛型擦除后的迭代类型**：通过 `javac` AST 定位增强 `for` 循环，并回溯原始字节码的 `iterator → hasNext → next → CHECKCAST` 链条精准恢复元素转型（首批消除 35 个文件、59 处编译错误，并经负例测试确认不会误插强转）。
- **异常重抛噪声**：构建仅供反编译参考的清理视图，仅当原指令与异常类型最终汇聚至同一真实 handler 时允许折叠，随后对照原始字节码复核。

## 6. 静态值流校验与双端隔离对照

为超越“零编译错误”的浅层验证，建立了静态与动态两层校验机制：
- **静态关系值流检查**：同步跟踪原/新字节码的指令位置、局部变量槽与操作数栈值身份，允许纯栈搬运与透明跳转差异，要求方法调用、堆副作用、条件分支及有序异常 handler 严格配对（`Main.main` 历史快照核验覆盖 301 个配对状态、366 条后继，含 66 条异常后继）。
- **双端隔离运行对照**：针对协议注册与加密（`Rp/Ca`）、多组动态枚举（9 owner / 54 常量 / 54 次独立 JVM）及文件资源清理（`HX`，覆盖短尾、关闭异常与 suppressed 异常）分别在独立新 JVM 中对比原/新行为，并构造刻意破坏的负例验证比较器的拒收能力。

## 7. 安全审计与运行依赖治理

在进入本地开发前，从考古研究树分出独立清理分支，对应用类与隐藏载荷进行入口排查，处置以下 7 类已确认风险：

| 风险类别 | 审计发现 | 处置措施 |
| :--- | :--- | :--- |
| 破坏性反分析 | 原始地址 `Unsafe.getByte(0)`、无界内存分配、`IntegerCache` 篡改、异常强退回调 | 6 个回调恢复正常父类返回；5 个高危默认桥改为抛出 `SecurityException` |
| 进程与系统命令 | 进程枚举、泛化 OS 命令执行桥、shell 打开路径 | 禁用进程枚举与默认 `exec` 桥；目录打开改用受控 API |
| TLS 与认证校验 | 全局 trust-all 证书/主机名放行、反射篡改 authlib 白名单 | 恢复系统默认证书与主机名校验，关闭第三方改写 |
| 隐蔽网络通信 | 旧云端请求、崩溃全文上传、携带 token 的旧服务上报 | 阻断附加请求并明确返回失败，不伪造认证成功 |
| 动态资源加载 | reader 错误分支死循环、缺少长度上限 | 改为有界读取，校验精确长度与 `CAFEBABE` 魔数，确保流关闭 |
| 文件路径边界 | 存档、材质/着色器、`level://` 缺少路径遍历约束 | 校验根目录与合法路径分量，拒绝目录逃逸及跟随符号链接删除 |
| 全局代理认证 | 全局 `Authenticator` 可能向任意 HTTP challenge 泄露代理凭据 | 严格绑定目标 host/port，旧构造改为 fail-closed |

运行依赖统一锁定为 **43 份第三方库**（其中升级了 Log4j `2.0-beta9 → 2.26.1`、Netty `4.0.23.Final → 4.1.140.Final`，以及 Guava、Gson、Commons、HttpClient 等）。为兼容旧版 Mojang `authlib` / `realms` 对已移除 API（`PatternLayout.createLayout`、双参 `Futures.addCallback`）的调用，构建了两份仅重定向单条常量池 `Methodref` 至 `LegacyRuntime` 适配器的私有派生库，其余归档内容保持不变。第三方原生库（LWJGL / JInput 等）仅核对来源与文件差分，未做逐指令逆向审计。

## 8. 编译通过后的典型运行时缺陷分析

全量源码编译零错误后，通过自动化探针与本地协议夹具定位并修复了以下 7 类代表性运行时缺陷：

1. **注解元素被恢复为 `synthetic` 导致 `IncompleteAnnotationException`**：后处理保留了原始 `0x1441`（`synthetic`/`bridge`）标志，致使 Java 8 反射跳过注解元素 `Cp`。修正为保留标准 `public abstract`（`0x0401`），并全量扫描 35,750 份 class 排查同类注解。
2. **未绑定快捷键 `0` 与文本事件冲突**：默认未绑定键码 `0` 与文本/IME 事件产生的键码 `0` 碰撞，导致输入 `/` 等字符时异常触发所有未绑定模块。在事件分发入口显式过滤 `keyCode == 0`。
3. **区块读写临界区错位**：反编译器将队列锁字段误译为 `DataInputStream` 强转，并生成空同步块 `synchronized (this.agr) {}`，导致队列操作脱离锁保护。重构临界区后，按相同反编译模式修复了网络层另外 3 处 monitor 范围缺陷。
4. **存档落盘竞态与 `Stream Closed`**：flush 循环提前中止、writer 登记与回调退场存在并发竞态，且 region cache 在旧内置服务端完成最终保存前即被关闭。引入 `registrationEpoch` 代际机制与 drain/join 同步彻底消除该缺陷。
5. **第二次保存退出死锁**：`jstack` 显示客户端线程永久阻塞于 `Futures.getUnchecked(...)`，而消费任务的 Server thread 已退出。改写为轮询消费者生命周期与 `volatile` 运行状态的停服调度逻辑，在线程终止时自动取消未消费任务。
6. **普通世界村庄生成空指针**：子构造器缺失 `super(null, 0, random, blockX, blockZ)`，导致隐式调用了供 NBT 反序列化使用的空构造器。补回父构造调用后，全面核查了 74 个结构类、151 个构造器。
7. **Netty 4.1 direct `ByteBuf` 无 backing array**：单人 `LocalChannel` 未暴露该问题，真实 TCP 路径分配 direct buffer 后，旧式 `new String(this.readBytes(j).array(), Charsets.UTF_8)` 抛出 `UnsupportedOperationException` 并泄漏临时 buffer。修改为 `this.readCharSequence(j, Charsets.UTF_8).toString()`，并通过覆盖 heap/direct/slice/pooled 的 13 组回归用例验证。

## 9. 阶段结论与可复用经验

- **交付基线与验证边界**：最终 `1.6.3` 审计基线包含 **25,004** 份 Java 源码与 **43** 份锁定依赖（最终安全归档保留 **10,368** 份隐藏载荷），一次 Java 8 全量编译及 119 步后处理通过；通过普通世界与村庄生成、625 个磁盘区块重读、重复保存退出、ClickGUI/配置读写及本机协议 `47` TCP + 双向 zlib 压缩连接回归，并具备实际多人游玩观察。*(注：该基线尚留旧式 LegacyPing 的 direct-buffer 边界；后续独立增量修复解决了三处 backing-array 假设与两处出站提前释放问题，并通过 18 用例 / 154 断言的 Netty pipeline 回归，但当时安装验收版仍保持原基线。)*
- **与 `OpenRemix` 主分支的关系**：`1.6.3` 完成了“可干净重建与安全运行”，但全局仍保留 `Class_<hash>` 命名且依赖 119 步后处理。消除保护层、全树语义重命名与脱离后处理的完整工程化工作落地在 **`1.7.1`** 主分支中。
- **可复用的工程经验**：
  1. 先独立拆解加载层与载荷身份，再进入常规字节码清理；
  2. 所有常量折叠与代理展开均须配合副作用审计与负例测试；
  3. 尽早构建自动化实机回归（磁盘重读、重复停服、真实回环 TCP），相比人工交互更能高效暴露隐蔽恢复缺陷。
